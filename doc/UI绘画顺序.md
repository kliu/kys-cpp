# UI绘画顺序

## 目的

UI 绘制方案的共同目的不是单纯减少绘制调用，而是让文字在最终显示的像素坐标中绘制，避免先写入较低分辨率的场景纹理、再随场景整体放大而变模糊。

游戏逻辑使用 UI 坐标。场景通常先绘制到逻辑分辨率的主纹理，随后再缩放到窗口。若文字也提前绘制到主纹理，就会和场景一起被缩放。当前方案和独立 UI 纹理方案都将 UI 从这一步缩放中分离出来，以保持文字清晰。

## 当前方案：命令队列直接绘制到窗口

当前 `UIRenderer` 记录文字、纯色矩形和纹理等 UI 命令。逻辑、脚本或控件调用绘制函数时只写入队列，不立刻调用 SDL 绘制。

一帧的顺序如下：

```text
场景绘制到主纹理 tex_
    -> 主纹理按 present rect 缩放并绘制到窗口帧缓冲
    -> UIRenderer 执行队列，按 present rect 将 UI 坐标换算为窗口像素坐标
    -> Font::renderText 和其他 UI 命令直接绘制到窗口帧缓冲
    -> renderPresent
```

`Font::executeDrawCalls()` 在主纹理绘制到窗口之后、提交窗口之前执行。此时文字字号和位置已经按窗口实际像素换算，因此不会再被缩放。

### 优点

- 不需要额外的 UI render target，也没有其创建、清空、重建和合成成本。
- 窗口尺寸、DPI 或旋转变化时，只需重新计算 `present rect`，不必重建 UI 纹理。
- UI 总在场景之后绘制，层级稳定。
- 队列保留调用顺序，脚本 `DrawRect`、`DrawString` 和 UI 图片的覆盖关系可预测。
- 少一次全屏纹理合成和 render target 切换。

### 限制

- UI 命令通常每帧重新执行，静态内容没有天然缓存。
- UI 不作为独立 GPU 纹理存在，不便单独截图、录制或做后处理。

## 独立 UI 纹理方案

可以创建专门的 `ui_overlay_` render target，把 UI 命令画入该纹理，再将其叠加到窗口。

若要保持文字清晰，`ui_overlay_` 应采用窗口实际输出像素尺寸，绘制时仍将逻辑 UI 坐标按 `present rect` 转成纹理像素坐标。一帧的顺序如下：

```text
场景绘制到主纹理 tex_
    -> 切换到 ui_overlay_，清空为透明
    -> 按 present rect 换算 UI 坐标，将 UI 命令绘制到 ui_overlay_
    -> 主纹理缩放并绘制到窗口帧缓冲
    -> 将 ui_overlay_ 按 1:1 叠加到窗口帧缓冲
    -> renderPresent
```

UI 纹理不能使用逻辑 UI 尺寸后再整体放大，否则文字仍会模糊，失去该方案的主要意义。

### 优点

- UI 可以作为独立图层缓存、截图、录制或进行后处理。
- 长期不变且绘制昂贵的 UI 可保留在纹理中，避免每帧重画。
- 可对 UI 单独实现淡入淡出、模糊、颜色处理或转场。

### 成本与注意事项

- 输出像素尺寸变化时必须重建 `ui_overlay_`，包括窗口 resize、DPI 变化和旋转。应在下一帧比较实际输出尺寸后按需重建，避免在每个 resize 事件中重复创建。
- 每帧清空并重放所有动态 UI 时，会多一次 render target 切换和 `ui_overlay_` 到窗口的全屏合成，未必比当前方案更快。
- 必须设置透明清空和正确的 alpha blend mode，否则 UI 背景或叠加透明度会出错。
- 若 UI 与场景一样先画入逻辑分辨率纹理再放大，文字清晰度会下降。

## 选择建议

目前 UI 以对话、菜单、脚本文字和事件图片等动态内容为主，优先使用当前命令队列直接绘制到窗口的方案。它实现简单，文字清晰，且不增加 UI 纹理生命周期和合成开销。

当确认静态 UI 重绘已成为性能瓶颈，或需要 UI 独立截图、缓存、特效和录制时，再引入 `ui_overlay_`。即使采用独立 UI 纹理，也应保留命令队列：队列负责统一调用时机、坐标换算和绘制顺序，UI 纹理只改变最终命令写入的目标。
